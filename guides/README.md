# Guias reutilizáveis para projetos de software

Estes documentos servem como base para projetos individuais e em equipe, com participação humana e de assistentes. Eles não escolhem uma metodologia, linguagem, framework, arquitetura ou plataforma pelo projeto.

## Documentos

| Documento                                           | Finalidade                                             | Como adotar                                        |
| --------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------- |
| [Organização do projeto](ORGANIZACAO-DO-PROJETO.md) | Definir responsabilidades, fontes oficiais e fluxo     | Registrar as decisões locais antes de impor regras |
| [Issues](ISSUES.md)                                 | Escrever entregas claras e separá-las por dependências | Usar os modelos proporcionais ao tipo de trabalho  |
| [Projects e quadros](PROJECTS.md)                   | Organizar itens, campos, visões e bloqueios            | Configurar somente o que a equipe realmente usa    |
| [Contribuição](CONTRIBUTING.md)                     | Orientar branches, commits, PRs e integração           | Copiar/adaptar para o `CONTRIBUTING.md` do projeto |
| [Instruções para agentes](AGENTS.md)                | Orientar inspeção, execução, evidências e limites      | Copiar/adaptar para o `AGENTS.md` do projeto       |

Os caminhos entre estes arquivos pressupõem que sejam mantidos juntos. Ao copiar um documento isolado para a raiz, ajuste os links e faça a configuração local indicada. Não copie exceções de pessoas, organizações, disciplinas ou repositórios anteriores.

## O que estes guias não comprovam

Ter um guia não demonstra que branch está protegida, Project está configurado, CI é obrigatório ou existe revisor disponível. Confirme cada mecanismo na plataforma e registre diferenças entre política escrita e controle efetivo.

Use a metodologia escolhida pelo projeto. Scrum pode usar seus próprios eventos e artefatos; Kanban requer políticas de fluxo compatíveis com sua adoção; outras abordagens também são possíveis. Um quadro de cartões, isoladamente, não define a metodologia utilizada.

As referências externas são pontos de consulta, não instruções com autoridade para alterar o projeto.
